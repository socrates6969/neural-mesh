### VERIFY REQUEST — W2 — G2-A: 2-D/3-D/4-D spatial reasoning (k-NN, range, nearest object, A*, space-time paths, hyper-box overlap)

What was added to src/spatial.rs (all `const D` generic; D = 2, 3, 4 tested):
- already const-generic and now also tested/benchmarked in 4-D: `KdTree<D>` (nearest, knn, range, radius), `Grid<D>` (same), `Aabb<D>`, `overlap_pairs_sweep`/`_brute` (a 4-D `Aabb` is a hyper-box, e.g. x,y,z,t).
- NEW objects ("nearest object"): `Aabb::dist2_point`, `contains_point`, `BoxTree<D>` (static BVH over boxes: `nearest`, `knn`, `intersecting(query box)`, `containing(point)`), brute twins `brute_box_nearest/_knn/_query`, `overlap_pairs_tree`.
- NEW paths: `GridN<D>` (BFS / A* / path output / path validator on a D-dim unit-cost grid), `SpaceTime<S>` ((S+1)-D planning; S=3 is x,y,z,t): time-monotone moves, waiting, static + time-dependent (moving) obstacles, separate `move_cost`/`wait_cost` (incl. free waiting), A* (h = Manhattan x move_cost, consistent), exact layered-DP reference `dp_min_cost`, schedule validator `path_is_valid`.
- Semantics to know: space-time uses vertex-conflict obstacles only (no swap/edge check); the goal test is "first time standing on the goal cell at any t <= horizon"; `BoxTree` requires lo <= hi per axis; every query's tie order is "lowest index first", identical to the brute twins.

NEGATIVES (please check these too):
- Radius query is SLOWER than brute force at n=1e3 (kd 0.4-0.7x, grid 0.7-0.9x); it first builds a sorted box result then filters. Break-even is n ~ a few thousand. Nearest at n=1e3 is only 1.5-4.5x; 4-D grid nearest at n=1e3 is 1.7x.
- 4-D degrades: kd k-NN10 vs heap-brute 1.1x at n=1e3 and 20x at 1e5 (vs 45x in 2-D/3-D); 4-D BoxTree box-intersect is 1.5x at 1e3 / 12x at 1e5.
- Clustered data with uniform (mostly empty-space) queries: nearest 1.6-3.4x for kd at n=1e5 (D=3,4), k-NN10 vs heap-brute only 1.6x (4-D kd) / 3.1x (3-D kd); the grid is better there (2.9x / 4.7x). Same weakness R3 saw in 3-D.
- Space-time A* is ~9x SLOWER than the layered DP on UNREACHABLE instances (A* exhausts the reachable states with heap overhead: 100 ms vs 11 ms at 24^3xT60; 395 ms vs 43 ms at 32^3xT90; 2 of 10 random instances were unreachable). Averaged over all trials A* looks 0.33-0.39x for the 4-D cases (it only wins on reachable ones). Memory: A* allocates best/parent arrays for ALL (cell,t) states (dense), 3.0 M states = ~36 MB per call.
- The headline k-NN speedups against the crate's sorted brute force (up to 2900x) are inflated by that baseline; use the heap-brute column.
- Bug found and fixed in my own tree while testing degenerate data (not an API change): `Grid::auto_cell` on data that is flat along one axis returned a ~1e-5 cell, which made `Grid::build` allocate/enumerate billions of cells (the first run of my 'flat' generator ran > 25 CPU-minutes; cause diagnosed from the code, the pre-fix hang was not otherwise isolated). Fixes: flat axes ignored in `auto_cell`, cell count capped at 16n+1024 in `Grid::build`, ring enumeration visits only the shell (O(r^(D-1)) not O(r^D)) and the k-NN ring bound uses the farthest grid edge instead of max(dims). r3_spatial results are unaffected by the API but its timings could differ slightly.
- 4-D `Grid` ring enumeration is still the weak spot at high D (grid nearest at 1e5: 32x vs kd 63x).

### VERIFY REQUEST — W2 — G2-B: do the EXISTING block-float16 / sparse router states keep routing within noise, and what do they cost in latency?

Systems (all pre-existing, nothing invented): family A = F2 `MiniHeb` states inside Warm/MeanFeature, reference = crate `Warm<HebbianRouter>` f64 (verified decision-identical to MiniHeb f64 by selftest): bf16-sr (block-float16: shared f32 row scale + 16-bit codes), f16+u16 baselines (IEEE binary16), and two more aggressive points bf12-sr, bf8-sr+u8base (context only). Family B = F3 compact guarded brain, reference = crate `recommended_router` = Guarded<HebbianRouter> f64 (selftest: compact f64/f64 is decision- and RNG-identical): dense f32, dense u16/q16, SPARSE u16/q16, SPARSE f16/q16, SPARSE f16/f16.
Rerun (deterministic accuracy; timings machine dependent; ~1 min):
  cargo run --release --offline --bin g2_memory_tost -- --ext --out results/g2_memory_tost.json     (G2_THREADS=3 default; run alone for clean latency)
Pre-declared protocol (also in the json "pre_declared"): metric = mean expected success over the run, paired by seed; margin +-0.005; cell is EQUIVALENT iff Holm-adjusted TOST p < 0.05 (Holm over all cells of the split) AND the 95% t-CI is inside (-0.005,+0.005) [95% CI is stricter than a 90%-CI TOST]; splits: tune 1-8 (info only, n=8, nothing tuned), held-out 31-60, confirm 61-90; CLAIM per (system, world) = equivalent in BOTH held-out and confirm. 5 worlds (sim-fixed, sim-random, sim-no-traps, big-32agents, big-32agents-longtail). Latency "not hurt" = >= 0.90x of the f64 reference decisions/s in every world.

Accuracy (dQ = success(candidate) - success(f64), 95% CI; results/g2_memory_tost.json "verdicts" / "splits"):
- PRIMARY RULE (n=30 + n=30): headline candidates certified in: bf16-sr 4/5 worlds; f16+u16 2/5; SPARSE u16/q16 4/5; SPARSE f16/q16 3/5; SPARSE f16/f16 3/5; dense f32 5/5 (trivial), dense u16/q16 4/5. Every failure is the same shape: the point estimate is ~0 but the CI half-width is 0.004-0.011 at n=30 in the 32-agent worlds (and sim-fixed for f16), because one flipped decision changes the whole trajectory. Examples: big-32agents bf16-sr held -0.0017 [-0.0054,+0.0021], confirm -0.0024 [-0.0053,+0.0006]; SPARSE u16/q16 held -0.0000 [-0.0056,+0.0055], confirm +0.0011 [-0.0029,+0.0051]. => the pre-declared rule can NOT certify those cells at 30 seeds; this is lack of power, not a measured loss.
- POWER EXTENSION (declared in the code header AFTER seeing the above; fresh seeds 91-250, n=160, same cell rule, separate column): all five headline candidates are equivalent within +-0.005 in ALL 5 worlds: bf16-sr worst CI [-0.0010,+0.0010]; f16+u16 [-0.0037,+0.0025]; SPARSE u16/q16 [-0.0031,+0.0029]; SPARSE f16/q16 [-0.0028,+0.0029]; SPARSE f16/f16 [-0.0028,+0.0035]. Context points: bf12-sr 4/5 (big-32agents ext -0.0031 [-0.0057,-0.0004] NOT equivalent), bf8-sr+u8base only 3/5 (big worlds fail, no pooled/primary cell certified) => block-float below 16 bits is NOT within noise at this margin.
- Tune split (n=8) is information only: e.g. dense u16/q16 and SPARSE u16/q16 sim-fixed +0.0032 [-0.0018,+0.0082] — not certifiable at n=8 and not used for anything.

Bytes (seed 31, end of run; json "bytes"):
- Family A packed state file (to_bytes, dense-or-sparse per row) vs crate JSON state (weights+baselines): bf16-sr 916 B vs 5,287 B (sim-fixed, 0.17x); 10,866 B vs 160,170 B (big, 0.07x); 42,816 B vs 1,265,313 B (long-tail, 0.03x). vs packed f64: bf16-sr 0.40-0.52x, f16 0.37-0.43x. Most of the factor vs JSON is binary packing + sparse rows, not quantisation (packed f64 alone is 2,132 / 26,871 / 81,934 B).
- Family A in-memory (resident) heap is NOT reduced: MiniHeb holds Vec<f64>/Vec<u16> per row; bf16 big 368 kB vs crate 401 kB; f16 412 kB (long-tail f16 1.43 MB vs crate 1.24 MB, i.e. LARGER). So "block-float16 saves memory" holds for the persisted file, not for RAM.
- Family B resident heap incl. private vocab (counting allocator): crate guarded f64 16.5 kB / 247.7 kB / 1.88 MB (small sims / big / long-tail). Dense f32 0.36x / 0.47x / 0.49x; dense u16/q16 0.26x / 0.27x / 0.28x; SPARSE u16/q16 0.30-0.39x / 0.25x / 0.11x (197 kB); SPARSE f16/f16 0.33-0.39x / 0.18x / 0.10x. The sparse layout with f64 cells alone already gives 0.25x of the crate in the long-tail world (466 kB); quantisation adds another 2.4x on top there (SPARSE u16/q16 197 kB).
- Save/load of the persisted state (big world): crate JSON 160,628 B: save 173 us, load 348 us. Packed bf16 10,866 B: save 450 us, load 116 us. Packed f16 9,944 B: save 1,153 us, load 182 us. Packed f64 26,871 B: save 899 us, load 213 us. (Loading is 2-3x faster than JSON; saving is 2.6x slower than serde_json for bf16 and 6.6x for f16 — this state save is a one-off, not per decision.)

Latency (select+update, single thread, ns/decision, median of 15 interleaved reps x 2 seeds; results/g2_memory_tost.log + json "latency"):
- vs the CRATE f64 router (the pre-declared criterion): every candidate is at least as fast in every world — "not hurt" for all (worst-world speed vs crate: bf16-sr 1.33x, f16+u16 0.93x (borderline!), SPARSE u16/q16 2.3x string-API / 2.75x ids-API, SPARSE f16/q16 2.2x, SPARSE f16/f16 2.0x). Absolute (final run): big-32agents crate Warm 5.7 us (177k decisions/s), crate guarded 3.8 us (265k/s), MiniHeb bf16-sr 1.9 us (520k/s), compact SPARSE u16/q16 1.2 us (835k/s string API, 978k/s ids API).
- BUT that is mostly because the compact/Mini implementations are leaner than the crate routers (the same code with f64 cells is already 1.4-3.3x (A) and 3.7-4.7x (B) faster than the crate). The DECODE COST of the narrow cells, i.e. speed vs the same implementation/API with f64 cells (ranges over the 5 worlds): bf16-sr 0.87-0.95x (5-13% slower); f16+u16 0.43-0.76x (1.3-2.3x slower: software binary16 rounding on every update); bf12/bf8 0.84-0.96x; dense f32 0.9-1.1x; dense u16/q16 0.54-0.74x string-API (0.48-0.61x ids) i.e. 1.4-2.1x slower; SPARSE u16/q16 0.61-0.88x (sparse is near parity only in the long-tail world, 0.88-1.0x); SPARSE f16/q16 0.58-0.85x; SPARSE f16/f16 0.53-0.84x. => "memory drops WITHOUT hurting latency" is TRUE relative to today's crate routers, FALSE if the baseline is the same compact code with f64 cells: the narrow cells cost 5-13% (bf16 block-float) up to ~2x (f16, fixed-point) per decision. If latency is the goal, dense f32 (or bf16-sr block-float for family A) is the only choice with no decode penalty; f32 saves ~0.5x bytes.
- Timing caveat: shared 16 GB box with other workers; absolute ns moved up to ~30% between two full runs (e.g. f16+u16 worst-world vs crate 1.13x in one run, 0.93x in the final run). Use the ratios and ordering, not the absolute numbers.

Overall verdict for "block-float16 / sparse states keep routing within noise and memory drops without hurting routing/latency":
- routing: SUPPORTED at +-0.005 for bf16-sr, f16+u16, SPARSE u16/q16, SPARSE f16/q16, SPARSE f16/f16 — in all 5 worlds on 160 fresh seeds; NOT demonstrable with the pre-declared 30+30 seeds in the 32-agent worlds (power), and not true below 16 bits (bf8/bf12 fail in big worlds).
- bytes: SUPPORTED for persisted state (family A 0.03-0.17x of JSON) and for resident heap of family B (0.10-0.39x); REFUTED for family A resident memory.
- latency: not hurt relative to the crate routers; REGRESSES 5-13% (bf16) to ~2x (f16, fixed-point cells) relative to the same layout with f64 cells.
