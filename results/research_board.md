ROOT CAUSE, measured (serve_diagnosis in the json): serve.rs writes each reply with `writeln!(w, "{resp}")` on the UNBUFFERED TcpStream clone: a 194-byte reply issues 124 write() syscalls (one per JSON token) = 929 us per reply on loopback vs 8.9 us when the line is formatted into a String first / 9.5 us through a BufWriter (100x). With --stdio (no sockets) the same server does 14,987 decisions/s (33 us per request, JSON parse + command + JSON build, one global mutex): so the TCP mode is ~18x slower than the server's own CPU ceiling, and that ceiling (~15 k decisions/s) is the cap for ANY number of clients because of the global Mutex<Server>. I did NOT patch serve.rs (read-only for me); a BufWriter (or building the line first) in handle_conn/run_stream is a 2-line fix worth ~18x on TCP, and serving the compact brain directly would move the ceiling from 15 k to 0.5-2.5 M decisions/s/thread before JSON.

(5) GPU / compute note: router and mesh are scalar CPU code: 0.35-3 us per decision, state fits in L1/L2 (2 KB..250 KB). A GPU would need >10 us just to launch a kernel and move the inputs, i.e. more than the whole decision, so there is nothing to offload; no GPU dependency was added or is needed. The only component where an accelerator could ever matter is an OPTIONAL embedding model feeding the knowledge layer (hash_embed is CPU and 32-dim here); that layer's cost is the O(store) retrieval scan, not the router.
