### VERIFY REQUEST — R4-A1 — H1b compute-once embedding (`MemoEmbedding`, opt-in)

RESULT (plain): the same task text is encoded 2-4 times per decision when the library pieces are composed the way shortlab does (Knowledge + Warm<CaseRouter>); `MemoEmbedding` removes the repeats with decisions BIT-IDENTICAL on 30 seeds x 10 worlds x 2 encoders. It is NOT a win for cheap encoders (table lookup 0.18 us, hash 0.19 us): there the memo is neutral to 14-19 % slower per decision (the existing CachedEmbedding is slower still); it only pays for an encoder as expensive as MiniLM-through-ONNX (2.4 ms/text, results/f6_py_latency.json), where it cuts the modelled encoder cost 3.64 -> 0.98 calls/decision (per-decision memo, cap 4) and -> 0.39 (cap 4096, cross-decision repeats), i.e. 8.7 -> 2.4 -> 0.95 ms/decision.
WHERE THE DUPLICATES ARE (read from the code, then counted): ResearchSession::run_task encodes ONCE per task (`emb.embed_task`), `ingest` once per doc (no duplicate there); KnowledgeRouter::set_context_task once; serve.rs, tiered.rs, lessons.rs, compact.rs take ready vectors (0 encodes). The duplicates are in COMPOSITIONS: CaseRouter's `Embedder` closure is called by `local_mass` (Warm evidence), `posteriors` (select, learned arm) and `update` => 2-3 calls/decision, plus Knowledge's 1 => 3.6 measured; coupling.rs ReplayMemory hash-embeds the task in `similar` and in `add` (2 cheap 64-d hash calls, a different space, not shareable with the configured encoder). `MemoEmbedding::task_embedder()` returns exactly the `casebased::Embedder` closure type and `Arc<MemoEmbedding>` is an `Arc<dyn Embedding>`, so the wiring needs no change in casebased/knowledge/research (see results/h1_proposed_patch.md for the optional ResearchConfig knob).
NUMBERS (results/h1_embed_ident.json, h1_embed_ident.log; 30 seeds x 10 worlds x 2000 decisions = 60k decisions per world and encoder; worlds = f6 text streams: q, subj3, para, qpara, q-mixed50, q-k6, q-then-para, para-mixed50, subj3-mixed50, unique/no-repeat; arms baseline | MemoEmbedding cap 4 | MemoEmbedding cap 4096 | existing CachedEmbedding cap 4096):

Per world (baseline -> memo4 -> memo4096): q 3.74 -> .99 -> .14; subj3 3.83 -> .89 -> .02; para 3.68 -> .99 -> .20; q-mixed50 3.52 -> 1.00 -> .64; NO-REPEAT unique 3.47 -> 1.00 -> 1.00 (memo4096 gives nothing without repeats; cap 4 still removes the within-decision repeats).
  BIT-IDENTITY: per decision (anchor, agent, reward bits, retrieval hit ids + similarity bits), a digest over the stream, and the final posteriors/local_mass bits on 20 probe tasks: identical between all 4 arms on all 30 seeds x 10 worlds, for both the MiniLM table encoder and the hash encoder (`ALL ARMS BIT-IDENTICAL ... true`; the bin exits non-zero otherwise). The reward model is my own (best agent per concept 0.85 vs 0.30, independent of the pipeline internals), NOT f6's.

### VERIFY REQUEST — R4-A1 — H1c query-embedding + result cache with invalidation (`CachedIndex`, opt-in)

RESULT (plain): the query-embedding memo carries nearly all the saving; the result cache only saves the (here ~100 us) search, and is only worth its memory when the same query vector repeats AND writes are rare or selective invalidation is on. It never returned a stale result (0 mismatches over every query of every stream, both indexes, with and without writes, plus two unit tests). Cost when there are no repeats: within noise (-0.1 .. +1.6 % modelled; +0 .. 10 us/query measured, noisy).
`CachedIndex<I: MemoryIndex>` (src/memory.rs; `RemovableIndex` too): key = query f32 bits + k (exact compare), bounded FIFO. Default invalidation = ANY write (add, add_batch, remove, compact) clears everything. `.selective(true)` (exact-score backends only: Flat, Hnsw, FlatRm, HnswRm) keeps an entry on `add` unless the new vector can enter its top-k (`cos >= k-th score - 1e-6` or fewer than k results), on `remove` unless the entry contains the id; compact clears all. `impl MemoryIndex for Box<T>` added so it can wrap `Box<dyn MemoryIndex>`.
NUMBERS (results/h1_cache.json/.log; N=2532 MiniLM d384 memory, 4000 queries per stream, k=5, 1 write per 50 queries in the second block; modelled ms/query = measured CPU + encoder calls x 2.4 ms; "saved" vs no cache):
 Flat, no writes: repeat-heavy (93 % repeats): enc/query 1.000 -> 0.072; measured search 81 -> 6.4 us/query with the result cache (hit rate .928); modelled 2.48 -> 0.254 ms (emb cache, -89.8 %) -> 0.179 ms (emb+result, -92.8 %). zipf(1.1): 2.50 -> 0.60 (-76 %) -> 0.52 (-79 %). mixed50: 2.53 -> 1.46 (-42 %) -> 1.39 (-45 %). NO-REPEAT: 2.507 -> 2.507 -> 2.508 ms (0.0 %).
 With writes (1 per 50 queries): clear-all result cache collapses (repeat-heavy res hit .083, saving 88.9 % = the embedding memo alone), selective keeps it (res hit .928, 7.4 us/query, modelled 0.180 ms, -92.8 %); zipf .337 -> .788; mixed50 .020 -> .443.
 HNSW (patched) behaves the same (repeat-heavy no writes 91 -> 5.3 us/query; selective with writes 80 -> 16 us); recall@5 vs exact (flat truth at the same write state): cached answer minus inner answer = +0.0000 worst case over all streams/arms (selective on the approximate index returns a still-valid earlier answer, never worse here).
 Flat: all arms (none, emb, emb+result, emb+result selective) return identical (id, score bits) lists on every query incl. the interleaved writes: true.
 BYTES: result entry = query f32 vector 1.5 KB (3 KB selective, it also stores the normalised query) + k x 16 B; 960 KB for the 288 distinct queries of the repeat-heavy stream; 2-10 MB at 2000+ distinct queries.
STALENESS TESTS: unit `cached_index_never_stale_after_writes` (300 random add/remove-top1/compact steps on FlatRm: cached == uncached after every step, removed id never returned, HNSW inner: cached == inner after every write) and `cached_index_selective_never_stale_and_keeps_entries` (400 steps incl. adds that land inside a cached top-k: bit-identical to uncached after every op, kept>0, dropped>0, more hits than clear-all). h1_cache's verification pass (not timed): 0 mismatches.
NEGATIVES: result cache hit rate is bounded by repetition of the EXACT query vector (a paraphrase has a different embedding => miss); template-heavy synthetic stream repeats far more than real traffic likely does; the saving is dominated by the encoder model; with 2.5k vectors the search is only ~100 us so the result cache saves little in absolute terms (it matters more for large HNSW / ef 128+: 0.8 ms/query in memory_bench); selective mode on HNSW is a design choice (valid answer, not necessarily the list a fresh walk would return); retuning ef_search through the shared handle needs a manual `invalidate()`.

### Honest summary of what H1 does NOT show
- It does not show a quality gain from caching (none intended): all cached/memoised paths are bit-identical or equal-recall by construction/test.
- It does not remove the rare HNSW loss mode; it only detects/repairs it when the caller opts in (audit_and_repair), and nothing in the repo calls it by default (HnswRm::compact / LongKind::Hnsw would need a call in tiered.rs: see results/h1_proposed_patch.md).
- Nothing was validated on real traffic or a real encoder (2.4 ms is the f6 python latency used as a cost model).
