### VERIFY REQUEST — W18 — hnsw reverse-edge

RESULT: CONFIRMED (empirical). hnsw_rs 0.3.4 (registry copy, the one neural-mesh uses) writes every reverse edge into the neighbour's list at `l_n = new_point.p_id.0` (the new point's top level) instead of the loop layer `l` (hnsw.rs line 1245, `reverse_update_neighborhood_simple`). Effect measured over 200 independent builds per variant (120 iid + 80 clustered, M=16, ef_construction=200, cosine on unit vectors, the same sequential `insert_slice` calls neural-mesh's HnswIndex::add makes):
- UNPATCHED: every one of 200 builds loses items. Items that are not their own top-1 neighbour at ef=512 (k=1): 0.67 % (1k, d32 iid) / 0.67 % (5k d32) / 0.92 % (5k d384) / 1.14 % (30k d32) / 2.41 % (30k d384, a very hard geometry) of the stored items, clustered data 1.14-1.33 %. All of them are level>=1 points (23155 iid + 2777 clustered misses in total, ZERO misses on level-0 points). They are absent from the top-10 at ef=512 as well (absent_from_top10 == misses), so raising ef does not help: the structure has no layer-0 in-edge to them (layer-0 in-degree 0 for 10.4/61.8 level>=1 points at 1k d32, 368/1875 at 30k d32; BFS from the entry point over layer-0 edges reaches 10.7 fewer points per 1k build).
- PATCHED (one line, `l_n = l as usize`): 0 misses, 0 in-degree-0 points, 0 unreachable points in all 200 builds (every cell).
- recall@10 vs brute force (200 fresh queries per build, ef 50/100/200), paired by data seed (levels are OS-random so builds cannot be paired, only data), patched minus unpatched, 95 % t-CI over 20 seeds: iid 1k d32 +.0151/+.0123/+.0103; 1k d384 +.0165/+.0178/+.0149; 5k d32 +.0191/+.0172/+.0150; 5k d384 +.0102/+.0171/+.0240 ([+.0217,+.0263] at ef200); 30k d32 +.0238/+.0247/+.0233 ([+.0215,+.0250] at ef200; .9758 -> .9991); 30k d384 +.0018/+.0058/+.0086 (CI at ef200 [+.0029,+.0143]; absolute recall only .52, iid d384 at 30k is a hard regime). Clustered data: +.0093..+.0136, all CIs exclude 0, patched recall@10 = 1.0000 at 1k and 5k. So the unpatched recall ceiling is about .985-.99 (ef 200) and the loss is a large part of the "recall .96-.99" seen in research_board H2; the rest is normal ANN approximation (ef50 at d384 is .57 for both variants).
- neural-mesh's own wrappers show it (unpatched crate, results/g17_wrapper_iid_n5000_d384.csv, 20 builds, d384 iid): `HnswIndex::add` 1.10 % of items not own top-1 at default ef_search=64 (44.5 of 5000 even at ef 512), `add_batch` (parallel_insert_slice) 1.08 % (42.3 at ef512), `HnswRm::add` (tiered long store) 1.04 %, and after remove-10 % + `compact()` (rebuild via add_batch) 0.94 % of the live items. All 20 builds of every path had misses. I could not run the wrapper against the patched crate (that needs a Cargo.toml `[patch]`, which I did not touch); the patched crate with the identical cosine-distance + insert_slice usage had 0 misses in the harness.

EXPOSURE of neural-mesh: only when an HNSW backend is chosen; all defaults are flat. src/memory.rs `HnswIndex` (Hnsw::new(m=16, max, 16, efc=200, ..), add = insert_slice, add_batch = parallel_insert_slice); src/tiered.rs `HnswRm` (LongKind::Hnsw, opt-in; default LongKind::Flat; its compact() rebuilds with add_batch so the bug re-occurs after every compaction; the unit test config M=8 has P(level>=1)=12.5 %, worse); src/casebased.rs `CaseRouter::with_index(Box<HnswIndex>)` (default `new` uses FlatIndex; only a test uses HNSW); src/workmem.rs `IndexKind::Hnsw` (opt-in); bins memory_lab / memory_bench / r3_store. knowledge.rs, lessons.rs, serve.rs, mesh.rs: no HNSW. Consequence if HNSW is used: ~1 % of lessons/cases/records are permanently unretrievable by similarity search (including by their own embedding), independent of ef; the loss is silent (len() still counts them).

WORKAROUND needing no crate change (measured on the UNMODIFIED registry crate, results/g17_wk_*.csv):
1. BEST: call `hnsw.modify_level_scale(0.2)` (public API, `let mut`, directly after `Hnsw::new` and before the first insert; HnswIndex::new in src/memory.rs). Then P(level>=1) ~ 16^-5 ~ 1e-6 per point, so the buggy branch is essentially never taken. 0 misses in 78 builds (1k d32 x20, 1k d384 x20, 5k d32 x20, 5k d384 x10, 30k d32 x5, 30k d384 x3), and recall@10/latency equal to the patched crate: 5k d32 .9850/.9993/1.0000 (patched .9851/.9993/1.0000), us/query at ef100 502 vs 518 unpatched, 30k d32 850 vs 892 us (no measurable loss of speed from dropping the hierarchy up to 30k). It prints two lines to stdout each call (library println). Factor 0.5 is not enough (0.012-0.022 % lost at 5k, 8/20 and 4/10 builds). Not tested: >30k points (hierarchy loss could matter at 100k+).
2. ALTERNATIVE: vendor the one-line patch (vendor_g17/hnsw_rs_patched, `[patch.crates-io] hnsw_rs = { path = ".." }`), what ruvector-core does (its tests hnsw_issue_773_* describe the same root cause; I confirmed the source of the claim independently).
3. NOT recommended (measured, only partial): insert every vector twice with a 1e-3 jitter on the copy and dedupe by id ("djit") leaves 0.04-0.09 % lost, costs 2x build time/memory and lowers recall@10 at ef50 (.857 vs .899 at 30k d32, .485 vs .578 at 5k d384); re-inserting jittered copies of the level>=1 points that have layer-0 in-degree 0 ("rjit", 3 passes) leaves 0.02-0.10 % lost. Exact (non-jittered) duplicate re-insert does NOT help (smoke test only, 3 seeds at 1k d32, not saved to CSV: misses 5-12 per build vs 5-13 baseline) because identical vectors give the diversity heuristic degenerate neighbour lists. Larger ef does not help at all (misses identical at ef 64 and 512). Insertion order does not matter (levels are drawn at random, order-independent).
