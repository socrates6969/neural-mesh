### VERIFY REQUEST — R9-C — DOCUMENT EXTRACTION + VERIFICATION (h19_*): research papers, financial statements, business documents

**Honest framing (read first).** Everything below is a SEEDED SIMULATION on documents I generated, plus a small unlabelled real-text check. All numbers are SYNTHETIC until validated on real traffic. The question measured is: given a hand-written extractor and an independent verifier, how much better does the SYSTEM answer document questions (ratios, growth, argmax, claim counts, contract dates/amounts) than a model that reads the text directly? It does NOT make the frozen LLM smarter. The "model reads text" arm is a seeded NOISE MODEL whose constants are ASSUMPTIONS (down.rs header); I swept them, and the sign of the headline depends on them for strong readers (see sensitivity). The extractor/verifier are real code run on real generated text; the reader is not.

New files only (mine): `src/bin/h19_common/{mod,gens,genb,scan,verify,cal,down}.rs`, `src/bin/h19_{corpus,extract,down,real}.rs`, `results/h19_*`, `results/h19_proposed_patch.md`, `results/lessons_h19.md`. No `src/*.rs`/Cargo.toml edits, no network/crates/models, no git commit. Reused lib APIs: `router::{Router,Rng,Task}`, `baselines::{Keyword,EpsGreedy,PooledThompson}`, `hebbian`, `prior::Warm`, `defaults::recommended_router`, `hybrid::Bm25`, `stats::{paired_diff,paired_t_pvalue,holm_adjust}`.

Rerun (director, alone on the box, ~12 min, deterministic; corpus FNV `03bbc9bf...` for seeds 31-60 must reproduce):
`bash results/h19_run_all.sh`  (builds; corpus hash+samples; tune; extract eval/inject/adv/narrow for tune/held/confirm; downstream eval+controls; sens; real).
Single commands (prelude: `export CARGO_TARGET_DIR=C:/Users/mariu/nm-target-r5 RAYON_NUM_THREADS=2; B=$CARGO_TARGET_DIR/release`):
`$B/h19_corpus.exe hash --seeds 31-60` -> `docs 2700 chars 3569869 facts 70296 fnv1a 03bbc9bfabf34686`
`$B/h19_extract.exe eval --seeds 31-60 --tag held` | `... --narrow` | `$B/h19_extract.exe inject --seeds 31-60 --tag held` | `adv --seeds 31-60`
`$B/h19_down.exe eval --seeds 31-60 --tag held` | `controls ...` | `sens ...` ; `$B/h19_real.exe --show 12`

**Protocol.** Tune seeds 1-8 (extractor/verifier written against Bank::Dev documents of seeds 1-8 only; tau=0.5 and repair=on chosen by `h19_down tune`, objective acc(ext+ver)-0.03*cost, then frozen in `results/h19_tune.json`), held 31-60, confirm 61-90 with the frozen config, paired 95% t-CI, Holm over arm x world (15 comparisons), 3 INDEPENDENT generators (paper / financial / business, own generator code, own seeds). Best fair baseline = plain reader with the best of {keyword, eps-greedy, pooled-thompson, hebbian-robust, warm(hebr), guarded-safe} PICKED ON THE EVALUATION SEEDS (favours the baseline); treatment arms use hebbian-robust only. TOST margin +-0.01 declared in code before any run. Post-hoc changes (disclosed): (1) noise grid in `sens` extended downward (0.02, 0.05) after the first held run because break-even was not bracketed; (2) the "no scale check"/"span re-parse only" ablation arms leaked the scale mismatch through the span check; fixed (`verify.rs` `enabled` guard) and `sens` re-run; main arms are unaffected (default config has every check on); (3) during DEVELOPMENT on tune seeds I fixed generator/extractor/verifier bugs (CSV-vs-thousands-comma split, bold cells, `iparse` for sci-notation / leading-dot / `KB`, KPI scale in the row label). Nothing was changed after looking at seeds 31-90 except (1) and (2).

**Corpora (all generated by seeded code; label SYNTHETIC unless REAL).** 3 worlds x layout L0..L4 (L0 clean markdown table / `Label: value`; L1 whitespace-aligned; L2 CSV or dot-leader or bullets; L3 footnotes, restatement, +-/bold, prose KPIs; L4 transposed or footer-scale or duplicated as-reported columns, mixed units, header scale) x two phrasing banks: `Dev` (the extractor was built on these) and `Unseen` (synonyms, `'000`/`mn`/`Mio`, unicode/trailing minus, EU/space thousands, "Current year/Prior year", seconds, new claim verbs/hedges/structures). The Unseen bank was written by me BEFORE the extractor, but the same author wrote both, so the real-world unseen gap is likely WORSE than reported. Sample docs: `results/h19_corpus_samples.txt`. Fact types: table_cell, param, claim (citations, hedges, negations), line_item (income/balance/cash-flow; scale, parentheses negatives, restatement, footnotes), date, amount, party, kpi, clause. Documents carry distractor numbers (years, note numbers, p-values, addresses, setup fees).

**1. Extraction accuracy (extractor at tau=0.5; P/R/F1 per field type; confirm numbers in parentheses)**
Seen phrasing (dev bank): ALL P 1.000 R 0.989 F1 0.995 (conf. 0.992/0.996); every field type 1.000 except line_item R 0.981 (L3/L4 financial 0.96). This is NOT a skill claim: the extractor was built on this bank (tune-seed F1 1.000). A dev-calibrated tau is meaningless (tau* = 0.05 at F1 1.000, `h19_tau.log`) because the dev bank contains no wrong extractions.
Unseen phrasing (held 31-60): ALL P 0.785 R 0.390 F1 0.521 (conf. 0.799/0.393/0.527). By field: table_cell F1 0.902, clause 0.713, party 0.551, date 0.504, param 0.493, amount 0.327, claim 0.276, line_item 0.376, kpi 0.161. By world x layout (unseen F1): paper 0.76-0.82, financial 0.27-0.48, business 0.33-0.42; NO monotone difficulty ordering L0->L4 for unseen text (phrasing dominates layout). 21.8% of candidates abstain (conf. 22.1%); ECE of confidence vs correctness 0.095 (0.124); span-exact 98.7%. Lesson re-confirmed from g13/g21: extractor accuracy collapses on phrasing it was not built for.

**2. Verifier: catch vs false-flag (kept = above tau, then verified)**
Natural extraction errors on unseen docs (held): 3766 wrong / 13710 correct kept facts. Full verifier CATCH 0.787 (conf. 0.791), FALSE-FLAG 0.0232 (0.0229), dev-bank false-flag 0.0000 (0 wrong to catch). Repairs proposed 2742, correct 2735 (99.7%). Reason mix on wrong facts: scale 1603, ambiguous separator 863, plausibility 225, claim-coverage 214 (but 309 flags on correct claims: a doc-level "claim set incomplete" flag, the only noisy reason), span 49, cross-check 11, footing 0 (natural errors rarely break an accounting identity, they break a whole column uniformly). After removing flagged facts: ALL P 0.785 -> 0.943, R 0.390 -> 0.381.
**SHARED-BLIND-SPOT ablation (`--narrow`, verifier restricted to dev knowledge, no `'000`/`mn`/`Mio`/unicode minus/EU separators):** CATCH 0.120 (conf. 0.127), same false-flag 0.0232. The 0.79 above is therefore an upper bound that exists only to the extent the verifier's author anticipated the variants; this is the same lesson as g13/g21 (independent verifier 90% vs shared 19%) and is the single most important caveat.
Injected single errors (held, each into an otherwise verifier-silent doc): scale x1000 / /1000 / sign flip / adjacent-digit transposition / decimal /10 with the SPAN LEFT UNCHANGED: catch 1.000 (n ~11-12k each), repaired to truth 97.5%. This is the easy class (value disagrees with its own source text) and is caught by the span re-parse alone. The hard class, WRONG CELL (value and span both move to the neighbour cell): line_item 0.87 (footing), KPI 0.60-0.67 (change-column / commentary cross-check), paper table_cell 0.12-0.15 (no redundancy in a results table), ALL 0.45-0.47, repair 0. Baseline false-flag on correct facts 0.65%.

What the extraction arms did (held, share of questions): paper ext: 89.4% exact&right / 4.3% exact&silently-WRONG / 6.3% fell back to a full read; ext+ver: 88.5 / 0.1 / 11.4. financial ext: 72.0 / 1.6 / 26.4; ext+ver 73.1 / 0.5 / 26.4. business ext: 68.0 / 1.8 / 30.2; ext+ver 69.0 / 0.7 / 30.2. So verification mostly converts silent errors (paper claim miscounts via claim-coverage fallback) into fallbacks; extraction's gain comes from exact arithmetic and a short read, with ~26-30% of financial/business questions falling back to plain reading anyway on unseen phrasing.
Costs: arms are cheaper than plain (0.36-0.40) ONLY because exact answers need no full LLM read (tool 0.05 + question->spec step 0.10 + verifier 0.02 + re-read 0.15/field + full fallback 1.0). If the spec step is not that cheap or fails more often (E_SPEC=0.02*agent), the gain shrinks; constants in `down.rs`.

**4. Controls and failures (all reported; held / confirm)**
* no-structure prose and tiny single-fact docs (extraction unnecessary), 4 extraction arms vs plain: every diff within +-0.0017, TOST equivalent at +-0.01 (all true, both splits). It is NOT free: cost 1.15-1.18x plain (tool + spec + the fallback read) - a measured loss on control docs.
* uninformative verifier (random flags on 15% of kept facts, no repair) vs ext: -0.0094 / -0.0099, TOST NOT equivalent, NOT non-inferior at +-0.01 (borderline FAIL), cost 0.428 vs 0.360. A bad verifier is not harmless.
* adversarial financial layouts: side-by-side two statements: left half extracted (R 0.50, P 1.00) and these questions only need the left half so accuracy 0.97-0.98 (NOT really adversarial, weak control); wrapped labels and numbers split across lines: extractor finds nothing (R 0.00), arms fall back to plain read: accuracy = plain (0.848), cost 1.15-1.17x, zero silent errors. I did NOT construct an adversary that induces silent mis-assignment (e.g. blank cells collapsing columns); the silent-failure rate on real multi-column PDFs is unknown.
* verifier "no footing" arm is identical to the full verifier downstream (0.9387): accounting-identity footing never fired on natural errors; it only helps injected wrong-cell errors in financial tables.

Unseen share 0 / 0.4 / 1.0: plain 0.825/0.821/0.815; ext 0.978/0.924/0.848; ext+ver 0.978/0.939/0.885 (cost 0.17/0.40/0.73): with all-unseen text the extraction gain shrinks to +0.03 (ext) / +0.07 (ext+ver) at 0.73x cost. Verifier variants at 40% unseen: full+repair 0.9387, flag-only 0.9378, narrow 0.9319, no scale check 0.9351, no plausibility 0.9382, no claim coverage 0.9322, span-only 0.9279 (ext 0.9243): the claim-coverage check and the span re-parse carry most of the downstream gain; most question types (ratios, growth) are scale-invariant, so scale errors that wreck extraction F1 barely hurt downstream answers. tau 0.2..0.8: ext+ver 0.9388/0.9385/0.9387/0.9293/0.9283 (flat to 0.5, worse above; tau tuned in-sample on seeds 1-8).

**6. Real-text check (REAL, UNLABELLED; `h19_real.exe`)**
(A) 56 markdown tables in 23 of this repo's results/*.md (machine-written benchmark tables): extractor numeric parser agrees with a trivial parser on 85.6% of cells (disagreements: glued units like `15.017 µs`/`MiB/s`, `NaN`, bracketed CIs, arrows, `**x**` fragments; the extractor knows only the dev unit list); verifier independent re-parse disagrees with the extractor parse on 0/4167 cells after two verifier bugs found by this check were fixed (leading-dot `.5758`, `4.6KB`). (B) 275 tables in 131 vendored crate READMEs: agreement 91.1%, 0/1056 re-parse disagreements; total-row footing applicable to only 2 columns in 275 tables and both FAIL (non-additive "total" semantics) - accounting footing is a fiscal-statement check, not a generic table check. (C) 95 currency amounts in real prose (market-research.md etc.): the independent re-parse disagrees on 37 (39%), all of them a `B`/`M`/`K` magnitude suffix after the span (`$11.5B`) that the dev extractor does not read: a true extractor miss the verifier would catch. (D) 1885 interval triples `x [lo,hi]` in results/*.md: 6 containment "violations", all inspected and all matcher false alarms (wrong preceding token), 0 real errors found. No labels, so these are agreement/coverage numbers, not accuracy.

**NEGATIVES / HONEST LIMITS**
1. The reader-noise constants (E0, A_DIS, B_LEN, C_SCALE, C_LAY, E_ARITH, RET_MISS_ERR) are my assumptions. Results are conditional on them; the strong-reader regime reverses the unverified-extraction gain.
2. Hand-written scanners on clean-ish generated text are not real messy PDFs: no ligatures, hyphenation, column interleave, OCR noise, rotated tables, merged cells, images. The Unseen bank is author-written. Expect real unseen F1 below 0.52.
3. The verifier's 0.79 catch depends on the author knowing the unseen variants (narrow verifier: 0.12). Independent knowledge, not independent code, is what matters.
4. Verification mostly pays on paper claims (coverage fallback) in the downstream metric; extraction F1 losses to scale errors do not translate into wrong ratio answers.
5. Retrieval (BM25 blocks, k=2 + header block) is net negative; routing contributes ~0 here (small simulated skill spread); the session loops use the repo's Router implementations, not the g18 multi-step orchestration engine.
6. The doc type (paper/financial/business) is given to the extractor; real use would need a classifier (not built).
7. Extraction arms cost less than plain only under the assumed 0.05 tool + 0.10 spec cost; spec-step failure is modelled as a single Bernoulli.
8. Only a weak adversarial control was built (see section 4); silent mis-assignment on real layouts is unmeasured.
