## Round B1 — shared-store durability / union-correctness audit (src/store.rs)
Method: read the store write paths and wrote one failing-first unit test per suspected defect (run on the unfixed code, then fixed). Baseline lib suite: 352 pass; with the new tests before the fixes: 2 FAILED (named below); after: 355 pass, 0 fail.
Defects CONFIRMED by a failing test on the unfixed tree:
1. `append_lines`: after a crash leaves a torn last line (no newline), the next appended record is glued onto the fragment and LOST (test `append_after_torn_tail_does_not_lose_the_new_record`). Affects journal + lessons.
2. `put_docs`: a crash between the vector write and the doc write leaves an orphan vector row; the next put_docs appends after it so every later doc is paired with the WRONG vector (silent retrieval corruption; test `orphan_vector_row_does_not_misalign_later_docs`). The old comment claimed load "ignores" the extra row; it only does so at the tail.
Defects fixed on reasoning (not separately demonstrated pre-fix): (3) `read_jsonl` and `sync_folder` used `BufRead::lines`, which errors on invalid UTF-8, so a tail torn inside a multi-byte char (or a half-synced shared-folder file) would make the whole journal / the whole sync fail; now `lossy_lines` (test `torn_multibyte_tail_does_not_make_journal_unreadable` passes post-fix); (4) `compact_journal` read the journal before taking the lock, so an outcome appended by another process in between was dropped by the rename (lost update); lock now taken first (no deterministic unit test; concurrency argument only).
Not changed (noted): put_docs/merge dedupe docs by id only, so two machines using the same id for different text silently keep the first; near-duplicate text under different ids is handled only by `gc_docs`.
Verdict: **KEPT** (bug fixes, defaults/format unchanged, no performance-relevant change). No retrieval/routing metric moved; these are correctness fixes.

## Round B5 — measured retrieval value of SHARING a doc corpus across machines (`py/b1/b5.py`, real h10 store, R1 retrieval, 500 queries from the query-disjoint halves, 8 random-subset draws per cell; paired own vs union)
Model: each machine holds an independent random fraction f of the 6,831 docs (union coverage = 1-(1-f)^M). Own = machine 0; union = merge of M machines. Z-scores / BM25 statistics recomputed on each store (no leakage of the full corpus).
MRR over all queries (a query with no relevant doc in the store scores 0): f=.25: own .139 -> union M=2 .198 (+.059), M=3 .241 (+.102), M=4 .272 (+.133), M=8 .314 (+.175); f=.5: own .215 -> +.064 / +.098 / +.111 / +.123 (M=2/3/4/8; sd over draws .006-.011). Gain is ~coverage-proportional, so diminishing: at f=.5 M=4 captures 90% of M=8's gain; at f=.25 it is still near-linear up to M=4 because coverage is still low.
**Distractor cost (pure effect on queries ALREADY answerable in the own store):** union - own = -.030/-.038/-.043/-.044 (f=.25, M=2/3/4/8) and -.012/-.016/-.018/-.018 (f=.5): negative in 6-8 of 8 draws in every cell. Foreign docs displace some correct answers; the cost is 5-25% of the coverage gain (largest where the own store is smallest). Net is strongly positive in every cell.
Verdict: **CONFIRMED (measurement)**: corpus sharing across machines is a large retrieval win when machines hold partially disjoint knowledge, saturating as union coverage approaches 100% (it does not compound linearly past coverage), with a real, measured distractor cost (-.01..-.04 MRR on already-answerable queries). Caveats: random-subset overlap model (real machines overlap non-uniformly); queries sampled from ALL docs (no locality of use); one real corpus (Rust crate docs).

## Round B7/B8 — fusion-normalisation variants (local top-K z, max-normalised BM25, tanh squash, alpha .6/.8) on the item-disjoint real + domain folds (`py/b1/b7.py`, `b8.py`)
B7 (K=100/300, maxnorm l=.1..1, tanh): localz300 with cap 3 looked like +.021..+.030 realH / +.027..+.035 realS on all three folds; B8 grid (K 150-2000, cap none/3/5, alpha .6-.8) selected K=2000/cap3/alpha.8 on TUNE and verified at **+.12..+.18 real MRR (Holm p<1e-5, W/L 190-230 : 60-120)** - far too large to be true.
**Self-found evaluation artifact (loud):** `rr_of` ranked with strict `>`, i.e. TIES COUNT IN FAVOUR of the relevant doc. A score CAP (min(z,3)) saturates many top candidates at the same value, so the relevant doc 'ties for first' and gets rank 1. With ties counted AGAINST the relevant doc (`>=`, now the default in `b4lib.rr_of`) every cap gain disappears: the TUNE-selected rule (K=2000, no cap, alpha .7) is realH -.002..+.004, realS -.019..-.001 vs R1 (Holm n.s.), domain 0. No fusion-normalisation variant beats R1 (z over all docs, .7/.3). Verdict: **REJECTED (all)**; B7's numbers were contaminated by the tie bug and are not to be quoted.
Consequence for earlier rounds: continuous scores (dense + BM25 float fusion) have no ties, so B3/B4 numbers stand; but any candidate that produces tied scores (int4/binary vectors R11/R12, caps, integer scores, PCA+int8 near-ties) can look better than it is under the strict-`>` rank used by `py/b1/lib.Retriever`-based rank counts; all such rounds were negative or recipe-only, but the battery's `real_mrr` rank counting should be switched to tie-pessimistic before the next quantisation round (flag to Team A).

## Round B18 — persisted ANN served for the WRONG vectors after gc + put (`src/store.rs::open_ann`)
Defect (confirmed by a failing test, then fixed): the HNSW dump stamp was only `(n, dim)`. `gc_docs` (drops k near-duplicates) followed by `put_docs` (adds k docs) keeps `n` but changes the content, so `open_ann` reloaded the OLD graph and returned results for vectors that were no longer in the corpus (test `persisted_ann_is_rebuilt_when_content_changes_with_same_row_count`: a query equal to the freshly added doc returned a stale row with cosine .75 instead of the new doc at 1.0). Realistic trigger: periodic gc + ingest on a shared store, or `sync_docs_folder` replacing docs. Fix: the stamp also carries a 64-bit content fingerprint (doc ids in order + every vector bit); stamps without one are treated as stale (one safe rebuild on first open after upgrade). Cost on the real 6,831 x 384 store: reload 43.0 ms median with the fingerprint vs 44.9 ms without (15 runs each, noise-level). Retrieval of the dumped graph is unchanged (existing `ann_dump_reload_matches_rebuild` passes; lib suite 359 pass). Verdict: **KEPT (bug fix)**.
## Round B19 — long `gc_docs` loses concurrent writes (stale-lock break) (`src/store.rs`)
Defect (confirmed by a failing test): the store lock is declared stale after 10 s and silently broken by the next waiter, but `gc_docs` is O(n^2 d) and holds the lock for its whole run, so on a big corpus (> ~25-30k docs at d=384, estimated from the n^2 scaling; seconds at 6.8k) another process breaks the lock, appends a doc, and gc then rewrites docs.jsonl from its earlier snapshot, dropping that doc. Test (stale threshold lowered to 150 ms by a test-only override so a 2.4 s gc over 6,000 x 256 vectors with 50 duplicates is 'long'): WITHOUT the fix the doc added during gc is lost (`the doc added while gc ran must survive` fails); WITH the fix it survives. Fix: `Guard::heartbeat()` refreshes the lock file mtime every 64 rows of the gc loop.
