## Round B1 — shared-store durability / union-correctness audit (src/store.rs)
Method: read the store write paths and wrote one failing-first unit test per suspected defect (run on the unfixed code, then fixed). Baseline lib suite: 352 pass; with the new tests before the fixes: 2 FAILED (named below); after: 355 pass, 0 fail.
Defects CONFIRMED by a failing test on the unfixed tree:
1. `append_lines`: after a crash leaves a torn last line (no newline), the next appended record is glued onto the fragment and LOST (test `append_after_torn_tail_does_not_lose_the_new_record`). Affects journal + lessons.
2. `put_docs`: a crash between the vector write and the doc write leaves an orphan vector row; the next put_docs appends after it so every later doc is paired with the WRONG vector (silent retrieval corruption; test `orphan_vector_row_does_not_misalign_later_docs`). The old comment claimed load "ignores" the extra row; it only does so at the tail.
Defects fixed on reasoning (not separately demonstrated pre-fix): (3) `read_jsonl` and `sync_folder` used `BufRead::lines`, which errors on invalid UTF-8, so a tail torn inside a multi-byte char (or a half-synced shared-folder file) would make the whole journal / the whole sync fail; now `lossy_lines` (test `torn_multibyte_tail_does_not_make_journal_unreadable` passes post-fix); (4) `compact_journal` read the journal before taking the lock, so an outcome appended by another process in between was dropped by the rename (lost update); lock now taken first (no deterministic unit test; concurrency argument only).
Not changed (noted): put_docs/merge dedupe docs by id only, so two machines using the same id for different text silently keep the first; near-duplicate text under different ids is handled only by `gc_docs`.
Verdict: **KEPT** (bug fixes, defaults/format unchanged, no performance-relevant change). No retrieval/routing metric moved; these are correctness fixes.
