## Round B1 — shared-store durability / union-correctness audit (src/store.rs)
Method: read the store write paths and wrote one failing-first unit test per suspected defect (run on the unfixed code, then fixed). Baseline lib suite: 352 pass; with the new tests before the fixes: 2 FAILED (named below); after: 355 pass, 0 fail.
Defects CONFIRMED by a failing test on the unfixed tree:
1. `append_lines`: after a crash leaves a torn last line (no newline), the next appended record is glued onto the fragment and LOST (test `append_after_torn_tail_does_not_lose_the_new_record`). Affects journal + lessons.
2. `put_docs`: a crash between the vector write and the doc write leaves an orphan vector row; the next put_docs appends after it so every later doc is paired with the WRONG vector (silent retrieval corruption; test `orphan_vector_row_does_not_misalign_later_docs`). The old comment claimed load "ignores" the extra row; it only does so at the tail.
Defects fixed on reasoning (not separately demonstrated pre-fix): (3) `read_jsonl` and `sync_folder` used `BufRead::lines`, which errors on invalid UTF-8, so a tail torn inside a multi-byte char (or a half-synced shared-folder file) would make the whole journal / the whole sync fail; now `lossy_lines` (test `torn_multibyte_tail_does_not_make_journal_unreadable` passes post-fix); (4) `compact_journal` read the journal before taking the lock, so an outcome appended by another process in between was dropped by the rename (lost update); lock now taken first (no deterministic unit test; concurrency argument only).
Not changed (noted): put_docs/merge dedupe docs by id only, so two machines using the same id for different text silently keep the first; near-duplicate text under different ids is handled only by `gc_docs`.
Verdict: **KEPT** (bug fixes, defaults/format unchanged, no performance-relevant change). No retrieval/routing metric moved; these are correctness fixes.

## Round B5 — measured retrieval value of SHARING a doc corpus across machines (`py/b1/b5.py`, real h10 store, R1 retrieval, 500 queries from the query-disjoint halves, 8 random-subset draws per cell; paired own vs union)
Model: each machine holds an independent random fraction f of the 6,831 docs (union coverage = 1-(1-f)^M). Own = machine 0; union = merge of M machines. Z-scores / BM25 statistics recomputed on each store (no leakage of the full corpus).
MRR over all queries (a query with no relevant doc in the store scores 0): f=.25: own .139 -> union M=2 .198 (+.059), M=3 .241 (+.102), M=4 .272 (+.133), M=8 .314 (+.175); f=.5: own .215 -> +.064 / +.098 / +.111 / +.123 (M=2/3/4/8; sd over draws .006-.011). Gain is ~coverage-proportional, so diminishing: at f=.5 M=4 captures 90% of M=8's gain; at f=.25 it is still near-linear up to M=4 because coverage is still low.
**Distractor cost (pure effect on queries ALREADY answerable in the own store):** union - own = -.030/-.038/-.043/-.044 (f=.25, M=2/3/4/8) and -.012/-.016/-.018/-.018 (f=.5): negative in 6-8 of 8 draws in every cell. Foreign docs displace some correct answers; the cost is 5-25% of the coverage gain (largest where the own store is smallest). Net is strongly positive in every cell.
Verdict: **CONFIRMED (measurement)**: corpus sharing across machines is a large retrieval win when machines hold partially disjoint knowledge, saturating as union coverage approaches 100% (it does not compound linearly past coverage), with a real, measured distractor cost (-.01..-.04 MRR on already-answerable queries). Caveats: random-subset overlap model (real machines overlap non-uniformly); queries sampled from ALL docs (no locality of use); one real corpus (Rust crate docs).

## Round B7/B8 — fusion-normalisation variants (local top-K z, max-normalised BM25, tanh squash, alpha .6/.8) on the item-disjoint real + domain folds (`py/b1/b7.py`, `b8.py`)
B7 (K=100/300, maxnorm l=.1..1, tanh): localz300 with cap 3 looked like +.021..+.030 realH / +.027..+.035 realS on all three folds; B8 grid (K 150-2000, cap none/3/5, alpha .6-.8) selected K=2000/cap3/alpha.8 on TUNE and verified at **+.12..+.18 real MRR (Holm p<1e-5, W/L 190-230 : 60-120)** - far too large to be true.
**Self-found evaluation artifact (loud):** `rr_of` ranked with strict `>`, i.e. TIES COUNT IN FAVOUR of the relevant doc. A score CAP (min(z,3)) saturates many top candidates at the same value, so the relevant doc 'ties for first' and gets rank 1. With ties counted AGAINST the relevant doc (`>=`, now the default in `b4lib.rr_of`) every cap gain disappears: the TUNE-selected rule (K=2000, no cap, alpha .7) is realH -.002..+.004, realS -.019..-.001 vs R1 (Holm n.s.), domain 0. No fusion-normalisation variant beats R1 (z over all docs, .7/.3). Verdict: **REJECTED (all)**; B7's numbers were contaminated by the tie bug and are not to be quoted.
Consequence for earlier rounds: continuous scores (dense + BM25 float fusion) have no ties, so B3/B4 numbers stand; but any candidate that produces tied scores (int4/binary vectors R11/R12, caps, integer scores, PCA+int8 near-ties) can look better than it is under the strict-`>` rank used by `py/b1/lib.Retriever`-based rank counts; all such rounds were negative or recipe-only, but the battery's `real_mrr` rank counting should be switched to tie-pessimistic before the next quantisation round (flag to Team A).
## Round B9/B10 — feedback-trained re-ranker and a document-length prior on the real store (`py/b1/b9.py`, `b9b.py`, `b9c.py`, `b10.py`)
B9: top-100 candidates of R1; pointwise HistGradientBoosting / logistic regression on 12 per-(query,doc) features (fused/dense/bm25 z, raw cosine, bm25/max, ranks, ln doc length, query length, query-token coverage / doc precision); 3-fold CV over QUERY-disjoint folds (B9) and CRATE-disjoint folds (B9b, stricter: every query of a source crate is in one fold). Result (tie-pessimistic MRR vs R1): family S **+.009..+.040 in 12/12 (model x fold) cells, Holm p<=8e-3 in 10/12**; family H -.009..+.016, never significant. B9c ablation: (fused score, ln doc length) alone gives S +.023 (p=1e-5), all 12 features +.029; fused+ranks alone 0. B10: additive length prior beta*(ln len - mean) on R1: S +.006..+.008 at beta .2 (Holm <=1e-5 on all three crate folds), growing monotonically with beta (+.016..+.030 at beta 1), H +-.002, domain world B -.004..-.008 at beta .2 (item-level n=48, n.s.).
**Why this is NOT a general result (checked, loud):** the S queries' relevant docs are systematically LONGER than the corpus (mean 26.7 tokens vs 18.0 corpus mean; H family 18.1), i.e. a property of how the S set was built, so any learned length prior is learning the benchmark's construction. It would only transfer to a deployment where users' relevant passages are longer than average (which a feedback-trained prior WOULD learn - that is the honest use-case, but this benchmark cannot demonstrate it).
Verdict: **NOT CONFIRMED / not shipped** (measured in-family gain on S, artifact-explained; H neutral; domain B slightly negative). Kept as scripts only. Lesson for validity: report relevant-doc length (and other prior-leaking statistics) of each query family before crediting any learned prior.
## Round B11 — randomized model check of the shared-folder sync (`tests/b11_sync_model.rs`)
60 seeded schedules x 80 steps over 4 machines (local appends in two NON-ASCII world names, syncs in random order, transport faults: a machine's folder file truncated at a random byte, a file deleted, junk .tmp files), then a quiescent phase (3 sync rounds each). Invariant: every machine ends with EXACTLY the union of everything ever appended, no duplicates, no phantoms. Second test: 30 schedules with the shared GC cap (cap_per_world=25, 3 machines): after quiescence all machines hold the IDENTICAL set and none exceeds the cap.
Result: **PASS on the fixed tree (both tests)**. On the pre-B1 `store.rs` the first test FAILS immediately (sync/outcomes return an InvalidData error when a file is truncated inside a multi-byte character) = concrete evidence for the B1 lossy-read fix. No convergence, loss or duplication defect found in the sync protocol itself (including the documented 'self-healing' re-export after a peer file is truncated/deleted). Verdict: **KEPT (test only)**. Limits: single process, files on one disk (no real network-FS semantics), schedule space is random not exhaustive.

## Round B14 — federated ROUTER-STATE merge instead of journal replay (`src/bin/b14_statemerge.rs`; library `HebbianRouter::merge_sum`, opt-in; results/b14_{tune,held,conf}.{json,log})
Idea: machines exchange their learned Hebbian state (O(features x agents)) rather than raw outcomes (O(n)). Arms for session 2 on machine 0: cold | own replay | UNION journal replay (shipped) | STATE-MEAN (per-feature mean of rows) | STATE-SUM (rows summed over machines, rescaled to row_cap = the same rule as `update`). Machines HOMOGENEOUS (250 tasks, all types) or SPECIALISED (2 types each, B12); M=2,4; worlds random/fixed; routers plain Hebbian and Guarded `recommended` (inner learner merged, keyword gate cold = R34 recipe). Pre-declared candidate = STATE-SUM (chosen on TUNE 1-30: within +-.005 of union replay in 14/16 cells; state-mean was worse); verified on held 31-60 / confirm 61-90, Holm over 96 tests per split (H100/250/500 collected, 32 cells x 3 H).
Result, state-SUM minus union replay: **no Holm-significant loss in held; in confirm one near-miss (fixed world, plain Hebbian, 4 specialised machines, H100 -.0161, CI [-.0246,-.0076], Holm p=.054)**; same cell -.0076 held, -.0156 tune. For the Guarded router's inner learner the difference is -.0021..+.0018 in all 16 cells per split (CI inside +-.005). For plain Hebbian with homogeneous machines CI inside +-.01 in all cells; with specialised machines (M=4, H100) CI reaches -.016 / +.013 (not equivalent within +-.01 in those cells). state-MEAN is worse: specialised M=4 H100 -.0245|-.0231 (random, Holm .003|.017) and -.024|-.044 (fixed, Holm .001|.0002) -> REJECTED.
Size: merged state 5.6 KB JSON (32 features, constant) vs union journal 73 KB / 147 KB at 500 / 1000 outcomes (13x / 26x and growing). Library: `HebbianRouter::merge_sum(&[&HebbianRouter])` (+ unit test; matches the experiment's JSON merge exactly, max |diff| 0.0 over 48 cells); opt-in meta state not merged; NOT idempotent (merging a merged state double counts) so use it with per-machine OWNED state files (same ownership protocol as R48), recomputing from the latest set each time.
Verdict: **KEPT (opt-in, narrow)**: state-sum merge is a practical O(1)-storage substitute for journal replay (equivalent for the Guarded router and homogeneous machines; a small ~-.01..-.016 H100 loss possible for the plain Hebbian router with several specialised machines). Simulator only; hand-rolled sum rule, one pre-declared candidate.
## Round B15 — shared-folder CORPUS sync (`MeshStore::sync_docs_folder`, `meshstore sync-docs`, `py/b1/b15.py`; opt-in)
Gap closed: R48's folder sync covered outcomes + lessons only; knowledge corpora needed `merge_from` (full-store access). Protocol = R48 ownership: machine m owns `<m>.<ns>.docs.jsonl` (one JSON line per doc: id, text, tag, dim, base64 of a per-vector int8 code = 4-byte scale + dim bytes), atomic temp+rename; imports foreign shards (union by id, torn lines / invalid UTF-8 / junk .tmp tolerated), re-exports only own-origin docs; same id + different text = counted `conflicts` (local kept); dimension mismatch = `skipped`.
Unit tests: base64 + int8 round-trip (error <= half a quantisation step), 3 machines + conflict + torn UTF-8 tail + .tmp junk, idempotent, bad ids rejected.
End-to-end on the REAL store (b15.py): 4 machines each an independent random 40% of the 6,831 paragraphs (overlapping), 2 sync rounds through a folder via the CLI: machine 0 ends with exactly the union (5,905 docs, id-set equal, 0 duplicates, texts intact); dequantised-vs-exact vector cosine min .999932 / mean .999985 (own-origin docs exactly 1.0); retrieval R1 MRR over 500 queries: exact union .3492 vs synced int8 .3492, paired d +.00003 (90% CI [-.00009,+.00014], TOST +-.01 PASS, W/L 47/52); mean top-10 overlap .9996, identical top-10 sets 498/500. Folder 4.29 MB vs 16.6 MB for the f32 vectors alone (3.9x smaller, shards also carry text).
Caveat (design, inherited from R48): two machines syncing concurrently can each drop a shared doc from their shard on the strength of the other's stale shard; both keep their local copy and the next sync re-exports it (self-healing, transient only). Verdict: **KEPT (opt-in)**; ties to B5 (corpus sharing is worth +.06..+.18 MRR with partially disjoint stores, minus a distractor cost).
